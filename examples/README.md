# Sample outputs

These are **real dossiers generated by Cauzon**, not hand-written, so output
quality can be evaluated without running anything. Each is exactly what Cauzon
writes into DataHub via `save_document`, attached to the incident and to the
culprit asset (which is also tagged `root-cause`).

Regenerate them with:

```bash
PYTHONPATH=agent python scripts/build_examples.py
```

CI fails if they drift from what the agent currently produces.

## The three incidents

Each plants a fault a *different* signal has to catch — the framework is not
tuned to a single demo.

- [`nyc-taxi-freshness-incident.md`](./nyc-taxi-freshness-incident.md) —
  **freshness propagation.** The visible symptom is a 40% volume drop on
  `daily_revenue`, but Cauzon traces past the intermediate `trips_cleaned` to the
  true origin: `raw_trips` ingestion stalled two days ago.

  This one also carries the **decoy**. `marketing_spend` is stale, schema-changed
  and volume-collapsed, and it outranks the real cause 8.0 to 5.0 — but no
  lineage edge connects it to the symptom, so the proof gate rejects it. The
  rejection is recorded in the dossier under *Candidates rejected by the proof
  gate*. This is the behaviour the whole project exists for.

  Note also the **Recurrence** section: Cauzon found two prior dossiers for
  `raw_trips` by reading them back out of the catalog, and escalated the
  recommendation from "backfill this window" to "treat the schedule as the real
  defect."

- [`shop-schema-change-incident.md`](./shop-schema-change-incident.md) — a
  **silent schema-change break.** `weekly_sales` reports $0 revenue everywhere
  even though order volume looks normal. The cause is `raw_orders`, where
  `amount` was renamed to `order_amount` while the downstream transform still
  selects `amount AS revenue`. The captured transform SQL is the smoking gun, and
  the recommended fix is that same statement with the new column substituted —
  after confirming it exists in the live schema.

  Nothing here is stale. No freshness or volume alert would fire at all.

- [`app-join-fanout-incident.md`](./app-join-fanout-incident.md) — a **join
  fanout.** `session_metrics` session counts tripled overnight with no marketing
  change. The cause is `user_dim`, whose primary key stopped being unique after a
  reload, so every downstream join multiplies rows.

  Nothing is stale *and* nothing changed shape. Only a key-uniqueness signal
  finds this, which is why the signal set is plural rather than a single anomaly
  score. The recommended fix names the real join key, read from the schema.
